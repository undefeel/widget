## Change
Keep threshold alerts/settings unchanged. For reset alerts, match provider/window
name and require evidence of a real forward reset boundary: prior reset deadline
has passed at the current observation time, a valid new deadline is later, prior
measured usage was at/above the configured threshold, and new usage is below it.
Do not label a same-window decrease or a future deadline correction as a reset.
Preserve the prior behavior for timestamp-less windows only if evidence is
unambiguous; prefer no reset alert to a false one. Do not claim 100% availability
when new usage is 6%: localize the exact message "Лимит обновлён; использовано %@"
/ "Limit reset; %@ used" with Fmt.percent(actualUsage).

Retain existing persisted notify.sent key format and limit (trim over 300 to 150),
but retain newest keys by numeric trailing reset timestamp, with stable tie-break.
Do not introduce a new persistence schema or invalidate existing dedupe keys.
Extract small pure decisions if useful for deterministic checks and a test sink;
never post real notifications or modify the user's defaults in automated checks.
