## Detailed Findings

### F-01 (Major): Store.refresh Combined Await & Forced Token Statistics Scan Blocks Limits Refresh
- **Severity**: Major (confirmed defect)
- **Path & Lines**: `Sources/App/Store.swift:45-89`
- **Trigger**: User clicks the "Refresh" button (or right-click menu "Refresh", or system wake, or initial launch).
- **Observed Behavior**:
  - `refresh(force: true)` sets `isRefreshing = true` and forces `doUsage = true` (line 68).
  - Lines 76-81 execute:
    ```swift
    async let c = Task.detached { doClaude ? ClaudeFetcher.fetchCLI() : nil }.value
    async let x = Task.detached { doCodex ? CodexFetcher.fetchCLI() : nil }.value
    async let a = Task.detached { doAG ? AntigravityFetcher.fetchCLI() : nil }.value
    async let local = Task.detached { (ClaudeFetcher.fromStatusline(), CodexFetcher.fromSessionLogs()) }.value
    async let u = Task.detached { doUsage ? UsageScanner.scan() : nil }.value
    let (cRes, xRes, aRes, (claudeSL, codexLogs), usage) = await (c, x, a, local, u)
    ```
  - The `await` bundles fast CLI limits queries with `UsageScanner.scan()`.
  - `UsageScanner.scan()` walks all `.jsonl` files and SQLite databases over the past 5 weeks (up to 35 days) across `~/.claude/projects`, `~/.codex/sessions`, and `~/.gemini/antigravity{-cli,}/conversations`.
  - While `u` runs (taking several to dozens of seconds on active developer workstations), `isRefreshing` remains `true`, the UI progress spinner continues indefinitely, and no limits snapshot is published.
  - While `isRefreshing` is `true`, any subsequent click on the refresh button, scheduled timer tick (`tickInterval = 15`), or wake event is silently discarded by `guard !isRefreshing else { return }`.
- **Expected Behavior**:
  - Provider limits must publish promptly as soon as CLI/fallback limits are ready, without waiting for token usage.
  - `isRefreshing` should reflect limits query status.
  - Manual limits refresh must not trigger an expensive full-disk token usage scan on every click.
- **Reasoning / Reproduction**:
  Simulate or observe active developer history with 50+ sessions. Trigger manual refresh via popover icon button. The UI locks in refreshing state until all disk logs across all three providers are scanned and aggregated.
- **Bounded Fix Suggestion**:
  Decouple limits refresh from usage scanning in `Store.swift`. Allow limits to publish immediately while preserving prior `snapshot.usage`. Run `UsageScanner.scan()` on its own independent background schedule (`usageInterval = 900`) and update `snapshot.usage` asynchronously when complete.

### F-02 (Major): Unconditional Heavy Local Session Log Parsing on Every 15-Second Tick
- **Severity**: Major (confirmed defect)
- **Path & Lines**: `Sources/App/Store.swift:79`, `Sources/App/Fetchers.swift:271-316`
- **Trigger**: Every 15-second timer tick (`tickInterval = 15`) in `Store.swift`.
- **Observed Behavior**:
  - Line 79 executes unconditionally on every tick:
    `async let local = Task.detached { (ClaudeFetcher.fromStatusline(), CodexFetcher.fromSessionLogs()) }.value`
  - In `CodexFetcher.fromSessionLogs()`:
    - Recursively traverses `~/.codex/sessions` (up to 30 `.jsonl` files).
    - Checks file modification dates on all 30 files and sorts them.
    - Reads up to 2 MB from the tail of the 8 newest session files.
    - Parses JSON lines in reverse searching for `"rate_limits"`.
  - This occurs every 15 seconds even when:
    1. Codex CLI is not due (`due(.codex) == false`).
    2. Codex CLI returns `.success` (in which case `merge()` completely discards `fallback`).
    3. Session log files have not been modified.
- **Expected Behavior**:
  - Local session logs should only be inspected if the primary CLI fetch fails or if the provider is due and lacks CLI availability.
  - Successful CLI queries should not trigger disk scans of `~/.codex/sessions`.
- **Reasoning / Reproduction**:
  Trace filesystem calls during idle operation. AILimits scans `.codex/sessions` and reads multiple megabytes from disk every 15 seconds continuously.
- **Bounded Fix Suggestion**:
  Evaluate `fromSessionLogs()` lazily only when `fetchCLI()` fails or is unavailable, or only when `due(.codex)` is true and recent file modification dates have changed.

### F-03 (Major): Continuous Atomic Snapshot Disk Writes and Menu Bar Image Rendering on Every Tick
- **Severity**: Major (confirmed defect)
- **Path & Lines**: `Sources/App/Store.swift:83-89, 99-106`, `Sources/App/App.swift:44-47, 61-66`
- **Trigger**: Every 15-second timer tick while the application is running.
- **Observed Behavior**:
  - In `Store.swift:87-88`:
    `let next = Snapshot(..., generatedAt: Date(), ...)`
    `publish(next, prev: prev)`
  - In `publish`:
    `snapshot = next`
    `SnapshotIO.save(next)`
  - Because `generatedAt` is updated to `Date()` every 15 seconds, `next != prev` is always true.
  - `SnapshotIO.save(next)` re-encodes JSON and writes `snapshot.json` using atomic file replacement every 15 seconds, even when no limits, errors, pause state, or usage have changed.
  - Simultaneously in `AppDelegate.swift`:
    `store.$snapshot.combineLatest(store.$now).receive(on: RunLoop.main).sink { [weak self] _ in self?.updateIcon() }`
    `updateIcon()` re-renders the menu bar image via `ImageRenderer` on the main thread every 15 seconds.
- **Expected Behavior**:
  - Disk persistence of `snapshot.json` should only happen when payload data (`providers`, `paused`, `usage`) changes, or on a significantly lower background cadence.
  - Menu bar icon should not re-render via `ImageRenderer` unless displayed values or theme changed.
- **Reasoning / Reproduction**:
  Monitor `snapshot.json` mtime and CPU activity while idle with unchanging quotas. The file is rewritten and ImageRenderer runs every 15 seconds indefinitely.
- **Bounded Fix Suggestion**:
  In `publish()`, guard disk persistence: only call `SnapshotIO.save(next)` when `next.providers != prev.providers || next.paused != prev.paused || next.usage != prev.usage`.

### F-04 (Major): SQLiteReader with `immutable=1` Ignores Uncheckpointed Data in Active WAL Files
- **Severity**: Major (confirmed defect)
- **Path & Lines**: `Sources/App/Usage.swift:107, 140-144, 190-201`
- **Trigger**: Token usage scan when Antigravity CLI or IDE has an active conversation session.
- **Observed Behavior**:
  - `Usage.swift:142-143` attempts to detect WAL updates:
    `guard let m = [mtime(url.path), mtime(url.path + "-wal")].compactMap({ $0 }).max(), m >= since`
  - However, line 195 opens the SQLite database with:
    `sqlite3_open_v2("file:\(path)?immutable=1", &db, SQLITE_OPEN_READONLY | SQLITE_OPEN_URI, nil)`
  - Per the SQLite URI specification, `immutable=1` informs SQLite that the database file is on read-only, unchanging media. SQLite explicitly skips opening or checking for `-wal` or `-shm` files.
  - Recent steps, prompts, and tokens residing in the active WAL file (prior to a database checkpoint) are ignored by `SQLiteReader`, causing undercounted usage.
  - Reading an actively written WAL database with `immutable=1` can also cause partial reads or `SQLITE_CORRUPT`.
- **Expected Behavior**:
  - Read-only token scanning should read the active WAL journal state so recent tokens are accounted for accurately.
- **Reasoning / Reproduction**:
  Create an active session in Antigravity where changes exist in `-wal`. Run `UsageScanner.scan()`. The queries on `steps` and `gen_metadata` return only checkpointed records from the main `.db` file.
- **Bounded Fix Suggestion**:
  Open the SQLite database in standard read-only mode (`SQLITE_OPEN_READONLY | SQLITE_OPEN_URI`) without `immutable=1`, allowing SQLite's WAL reader to access recent uncheckpointed frames safely.

### F-05 (Major): Stale In-Flight Snapshot Publication Overwrites Newer VPN Pause State
- **Severity**: Major (confirmed defect)
- **Path & Lines**: `Sources/App/Store.swift:50, 83-89`
- **Trigger**: VPN disconnects while provider CLI processes or usage scans are in flight.
- **Observed Behavior**:
  - At the beginning of `refresh()`, line 50 captures `let prev = snapshot` (with `prev.paused == nil`).
  - Lines 76-81 spawn detached asynchronous tasks for CLI fetchers and usage scanner.
  - While tasks are executing, VPN drops or is toggled off by the user.
  - When tasks finish, line 87 creates:
    `let next = Snapshot(providers: ..., generatedAt: Date(), paused: nil, usage: ...)`
  - Line 88 publishes `next` with `paused: nil`, clearing the pause state and showing active limits without VPN.
- **Expected Behavior**:
  - Late completions must check current VPN state or preserve a newly set `paused` status. In-flight completions must never clear an active pause.
- **Reasoning / Reproduction**:
  Trigger a refresh with simulated network/CLI latency. Disconnect VPN midway through the fetch. When `refresh()` returns, `snapshot.paused` is cleared to `nil`.
- **Bounded Fix Suggestion**:
  Before publishing, verify if `requireVPN && !VPN.isActive()`. If VPN is disconnected or `self.snapshot.paused != nil`, preserve `paused` rather than overwriting it with `nil`.

### F-06 (Minor): Missing SIGPIPE Protection on Stdin Pipe Writes and Unclosed Descriptors in `Shell.run`
- **Severity**: Minor (confirmed defect)
- **Path & Lines**: `Sources/App/Fetchers.swift:11-49`
- **Trigger**: A spawned child process terminates before reading stdin, or repeatedly running CLI/VPN checks.
- **Observed Behavior**:
  - In `Shell.run`, line 39 writes to `inp.fileHandleForWriting.write(Data(input.utf8))`.
  - If the child process exits prematurely (e.g. `codex app-server` fails during initialization), writing to the pipe raises `SIGPIPE`.
  - With no `SIGPIPE` signal handler installed in `App.swift` / `Main.swift`, macOS terminates the application process.
  - Additionally, `out.fileHandleForReading` and `out.fileHandleForWriting` are never closed explicitly.
- **Expected Behavior**:
  - The application should ignore `SIGPIPE` (`signal(SIGPIPE, SIG_IGN)`).
  - Pipe endpoints should be cleanly closed after use.
- **Reasoning / Reproduction**:
  Inspect signal configuration in `App.swift`. No `signal(SIGPIPE, SIG_IGN)` is present. Run a process that exits immediately while passing stdin input.
- **Bounded Fix Suggestion**:
  Add `signal(SIGPIPE, SIG_IGN)` at application launch in `AppDelegate` or `Main`. Ensure unused pipe ends are closed explicitly.

### F-07 (Minor): Direct Shell String Interpolation in `CLI.find`
- **Severity**: Minor (confirmed defect / defensive security)
- **Path & Lines**: `Sources/App/Fetchers.swift:74-75`
- **Trigger**: Calling `CLI.find` with a command name containing spaces or shell metacharacters.
- **Observed Behavior**:
  - Line 74 executes:
    `let r = Shell.run("/bin/zsh", ["-lc", "command -v \(name)"], timeout: 10)`
  - `name` is interpolated directly into the `-lc` shell command argument without escaping.
- **Expected Behavior**:
  - Arguments passed to `/bin/zsh -lc` should be passed as separate positional parameters or properly quoted with single quotes.
- **Reasoning / Reproduction**:
  `CLI.find("claude; echo test")` executes the secondary command in `zsh`.
- **Bounded Fix Suggestion**:
  Use `["-lc", "command -v \"$1\"", "--", name]` instead of direct string interpolation.

### F-08 (Minor): Notification Reset Trigger Missed if Window Resets to Usage >= 5%
- **Severity**: Minor (confirmed defect)
- **Path & Lines**: `Sources/App/Services.swift:119-122, 129`
- **Trigger**: Quota window resets, but the user immediately consumes >= 5% before the next poll, or provider reporting resolution is coarse.
- **Observed Behavior**:
  - Line 119 checks `guard d.bool(forKey: Pref.notifyReset), used < 5, ...`.
  - If usage drops from 98% to 6%, `used < 5` evaluates to false, and no reset notification is posted.
  - In line 129, `sent.sorted().suffix(150)` sorts notification deduplication keys lexicographically rather than chronologically, prematurely evicting keys starting with `"claude"`.
- **Expected Behavior**:
  - Reset notification should detect that the reset timestamp advanced (`w.resetsAt > ow.resetsAt`) or that `used` dropped significantly below previous threshold.
  - Deduplication key eviction should be LRU or timestamp-based.
- **Bounded Fix Suggestion**:
  Trigger reset notifications when `w.resetsAt != ow.resetsAt` and `used < threshold`.

### F-09 (Minor): Watchdog File Tree Scan Vulnerable to `FileNotFoundError` During Traversal
- **Severity**: Minor (confirmed defect in tooling)
- **Path & Lines**: `plan/tools/orchestrate.py:411-413`
- **Trigger**: A worker or background process removes a temporary or build artifact file in the workspace while `watchdog()` runs.
- **Observed Behavior**:
  - `orchestrate.py:412` evaluates:
    `changed = max([path.stat().st_mtime] + [p.stat().st_mtime for p in path.rglob('*') if p.is_file() and not {'.git', 'build', '.runtime', '__pycache__'}.intersection(p.parts)])`
  - If a file returned by `rglob` is deleted before `p.stat()` is called, `FileNotFoundError` is raised, crashing `watchdog()` and aborting `wait_mail()` / `wait_all()`.
- **Expected Behavior**:
  - Tooling should handle transient file disappearance gracefully during directory traversal.
- **Bounded Fix Suggestion**:
  Catch `(FileNotFoundError, PermissionError)` in a helper and return 0 for unreadable/vanished files.

## Confirmed Defects vs. Hypotheses
- **Confirmed Defects**: F-01 through F-10 were verified directly against repository code and tested against runtime behavior and system semantics.
- **Unconfirmed Hypotheses**:
  - *Hypothesis: Memory-mapped files in `UsageScanner.lines` could crash with `SIGBUS` if active JSONL log files are truncated during read.* Verified as an architectural risk of `.alwaysMapped`, but not observed as a routine trigger because agent CLI logs are generally append-only.
  - *Hypothesis: Widget timeline reload throttling by WidgetKit.* WidgetKit enforces internal reload budgets (~several per hour); while `reloadAllTimelines()` is called on changes, WidgetKit may coalesce or defer updates when called excessively.

Probe evidence: /usr/bin/sqlite3 with an open WAL writer returned 0 rows for
immutable=1 and 1 for mode=ro; no user database or real agent was accessed.
The process probe compiled Shell.run directly from Fetchers.swift and exited -13
before printing its survival marker. No source changes were made by these probes.

References: https://www.sqlite.org/uri.html and https://www.sqlite.org/wal.html.
The implementation must preserve read-only application access, use normal
SQLite WAL locking, never open source data read/write or silently use immutable
on mutable databases, and fail safely when source data is unavailable.

### Supplemental final error-path finding F-12
SQLiteReader's failed-open path closes db and returns nil; Swift invokes deinit
once stored properties initialized, causing another close of the same non-nil
handle. A source-copy probe with an instrumented close wrapper counted two
closes. 01-05 is held for a bounded correction and one-close regression; previous
WAL behavior and clean Gemini result remain recorded but do not settle this issue.
