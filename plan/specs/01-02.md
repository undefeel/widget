## Target

The refresh button must show updated provider limits independently of a slow
local token statistics scan. Keep statistics useful and current in background
work. No regression in VPN behavior, fallbacks, widget snapshots or notifications.

Current baseline: `LimitsStore` in `Sources/App/Store.swift` is MainActor-bound.
`refresh(force:)` has one isRefreshing guard, forces UsageScanner on manual
refresh, and awaits three provider CLI results, a local fallback tuple and usage
before publishing a single Snapshot. UI and menu refresh entrypoints are
`Sources/App/Popover.swift:MainPanel` and `Sources/App/App.swift:refreshNow`.

## Change

- Commit a lead plan choosing the smallest compatible state/task design.
- Separate limits-refresh state/completion from statistics work. Limits must
  publish without waiting for usage; keep the last valid usage visible meanwhile.
- Manual limits refresh must not repeatedly restart/duplicate an ongoing usage
  scan. Statistics retain their background interval and resume/start behavior.
  Decide whether manual refresh schedules due statistics, without forcing a
  costly rescan on every click. Describe this behavior in README.
- Late usage completion must merge with the current provider snapshot; late
  limits completion must preserve newer usage. Prevent stale completions from
  reverting VPN pause state or resurrecting superseded data.
- Preserve the current VPN gate: when it blocks a request, do not start CLI or
  local history reads. Define what to do with already in-flight work when VPN
  policy/state changes, without claiming instantaneous cancellation of sync I/O.
- Preserve polling intervals, fallback rules, errors, notifications and widget
  updates. Avoid duplicate provider processes on timer/wake/button overlap.
- isRefreshing should represent limits work, so usage work alone cannot hide
  the refresh button/spin indicator indefinitely. Keep existing user wording
  unless an additional status message is necessary; localize any new message.
- Consider publishing ready providers incrementally if it is necessary to avoid
  a slow unrelated provider delaying all others; keep this within the scope and
  size limit. Do not change CLI/protocol contracts without a concrete finding.
- Introduce only minimal seams for deterministic tests. A standalone swiftc
  harness using fakes is permitted; no Swift package/Xcode/framework migration.

## Constraints

- Follow plan/TESTING.md.
- Do not change approved architecture/stack, dependencies, account credentials,
  provider authentication, or the user's installed application/preferences.
- English agent communication; preserve English/Russian product localization.
- Enumerate timer, wake, manual refresh, VPN pause/resume, usage completion and
  limits completion paths. No global serialization of unrelated limits and usage.
- Do not discard data on temporary failures or replace current state with a
  snapshot captured before an await. Use cancellation/generation fencing where
  needed and explain the invariant.
- Automated checks use synthetic data only; no real agent CLI/log scanning.
- Keep within about 1,500 changed lines; split luna pieces into at most 300 lines
  and 1–3 files. Do not split one concurrency invariant across parallel owners.

## Observable acceptance

only `Tests/run-refresh.sh` or a narrower harness selector chosen in the plan.

1. With immediate synthetic provider results and delayed statistics, limits and
   their refresh indicator complete before statistics; completion of statistics

   evidence; the test must not depend on real CLI latency.
2. Overlapping timer/wake/manual triggers and old/new usage/limits completions
   do not duplicate scans/processes or overwrite newer unrelated state. Include
   a valid alternative completion ordering in the same harness.
3. VPN-blocked refresh starts no provider/history reads; late in-flight results
   cannot clear a newer paused state. Exercise persisted/widget-visible snapshot
   contents, not only task flags. Existing fallback/error behavior remains valid.
